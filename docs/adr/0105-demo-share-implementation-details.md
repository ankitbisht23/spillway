# 0105. Public demo share: implementation details

- **Status:** Accepted
- **Date:** 2026-11-28
- **Requirement IDs:** SC-09, SEC-05, SC-08, SEC-02, SEC-04, CP-11

## Context

ADR-0097 settles the public demo: Caddy on 8888 (built by grafana-demo, ADR-0104), the tunnel, `make demo-share`, `make demo-share-stop`, `make demo-share-test` with a stand-in tunnel, the client IP from `CF-Connecting-IP` (SEC-05) and the realm hardening; ADR-0100 left `getDemo`'s `client_ip` and ADR-0103 §7 the client-IP function to this task. Building it (task demo-share, ADR-0093) left details open; accepted ADRs are not edited, so the choices are recorded here.

## Decision

1. **Client IP.** `SPILLWAY_CP_TRUSTED_PROXIES` is parsed by the gateway's `proxy.ParseTrustedProxies` (the same CIDR rules as `SPILLWAY_GATEWAY_TRUSTED_PROXIES`; a bad value stops the control plane, naming the setting) and read in every mode. The client-IP function of ADR-0103 §7 is the only one replaced: `CF-Connecting-IP` counts when the TCP peer (unmapped, zone dropped) is in the list and the request has exactly one such field line holding one IP address without a zone or port (surrounding spaces trimmed; an IPv4-mapped address counts as IPv4); otherwise the peer's address. IPv6 still counts per /64. `getDemo` gains the required response property `client_ip` (oasdiff: additive), the same string the caps count; the UI does not show it.
2. **Keycloak, the control plane and the gateways in the demo override.** `deploy/compose/demo.compose.yml` overrides `keycloak` (label `spillway.demo`, `KC_HOSTNAME: ${DEMO_KC_HOSTNAME:-http://localhost:8180/auth}`, `KC_PROXY_HEADERS: xforwarded`, `KC_PROXY_TRUSTED_ADDRESSES: 172.29.255.10/32`) as ADR-0097 §1 has it; so `make demo` now recreates Keycloak once (about a minute, the realm re-imported) and `make dev` recreates it back, which ADR-0104 §6 had avoided until this task. The control plane gets `SPILLWAY_CP_OIDC_ISSUER: ${DEMO_ISSUER:-…}` and `SPILLWAY_CP_TRUSTED_PROXIES: 172.29.255.10/32`, the three demo gateways `SPILLWAY_GATEWAY_JWT_ISSUER: ${DEMO_ISSUER:-…}`.
3. **The tunnel service.** `tunnel` (profile `share`): the pinned cloudflared image, `read_only`, no port, address 172.29.255.11, `TUNNEL_TOKEN` listed without a value (compose then takes it from share.sh's environment, which sets it only for `TUNNEL=named`; otherwise it is unset in the container) and `command: ${DEMO_TUNNEL_COMMAND:-tunnel --no-autoupdate --metrics 127.0.0.1:0 --management-diagnostics=false --url http://caddy:8888}`; `TUNNEL=named` sets the command to `… run`. cloudflared 2026.11.0's help (read offline, `--network none`) says that in a container its metrics listener binds every interface by default, so `--metrics 127.0.0.1:0` keeps it on the container's loopback ("metrics off" for everyone else), and `--management-diagnostics=false` turns off the remote diagnostics routes it serves through Cloudflare. `tunnel-stand-in` (profile `share-test`) is the `demo-traffic` image with `stand-in-tunnel --url https://stand-in.spillway.example` at the same address. Neither has `depends_on`: share.sh starts them with `--no-deps` once it has checked that the demo, and so Caddy, runs. The real tunnel was never started in this task (the run forbids it), so its two flags are checked only against the binary's help.
4. **Where the share's settings live.** share.sh writes `deploy/demo/run/share.env` (`DEMO_PUBLIC_URL`, `DEMO_KC_HOSTNAME`, `DEMO_ISSUER`, and the non-secret `DEMO_SHARE_UID`/`DEMO_SHARE_GID`, the invoking user's) and uses it with a third compose file, **`deploy/compose/share.compose.yml`**, which exists only for the share: it gives `demo-traffic` (read-only) and `demo-seed` (read-write, for `share-config`) the mount `./deploy/demo/run:/run/demo`, `SPILLWAY_DEMO_CLIENT_SECRET: ""` with `SPILLWAY_DEMO_CLIENT_SECRET_FILE: /run/demo/spillway-ci-secret` (ADR-0097 §3 step 6), and `user: ${DEMO_SHARE_UID}:${DEMO_SHARE_GID}`, so the `0600` secret files written by that user are readable on Linux hosts too (Docker Desktop maps owners itself). A conditional override inside `demo.compose.yml` would need nested interpolation and a bind mount whose source exists only during a share. `demo.sh` and `scenario.sh` add the file and `share.env` whenever `share.env` exists, so the fault switches and `make demo-d1 … d7` keep working during a share with the rotated secret; `make demo` and `make demo-reset` refuse to run during a share (each would recreate Keycloak, through its dependencies, without the share's admin password).
5. **share.sh details.** Precondition "the demo runs": the demo-labelled control plane and Caddy run and an anonymous `GET /api/v1/demo` answers 401 (demo mode on, a token needed), not demo mode off's 404; a 200 would need a token the script does not have. The values it needs are read from `SHARE_ENV_FILE` one `NAME=` line at a time (the last one, one pair of quotes dropped), never by sourcing the file. Recreates run as two `up --wait --force-recreate --no-deps` calls, Keycloak alone first, then `controlplane gateway-1 gateway-2 gateway-3 grafana-demo`, so the others start on the new realm and its keys; `DEMO_MODE=true` is exported for every call. `share-config` runs as a one-off of `demo-seed` (`run --rm --no-deps -e KEYCLOAK_ADMIN_PASSWORD -e DEMO_ADMIN_PASSWORD`, plus the two GitHub variables for a named tunnel; `-e NAME` passes each by name). If a step fails or is interrupted after the tunnel started, an `EXIT` trap runs `stop`, so no half-configured share stays public. `stop` is idempotent: it always removes the tunnel containers and the files in `deploy/demo/run/`, and recreates Keycloak and the changed services only when the demo's (demo-labelled) control plane runs, so after a `make dev` during a share it leaves the dev stack alone; `active` (a share runs) is true while `share.env` or a tunnel container exists. Keycloak updates send the whole `admin-ui` representation back and partial representations (`{"enabled": false}`, `{"bruteForceProtected": true}`) elsewhere.
6. **`share-check` and the extra checks.** Each check prints `share-check: <id> PASS|FAIL: <what it saw>` (URLs, statuses, booleans, the check container's own address). s9a and s9c compare `client_ip` with the check container's own address (the local address of a connection to the control plane), which is stricter than "not 203.0.113.7". s9b runs inside `tunnel-stand-in` (`docker compose exec`) and gets its token by a **browser login** through the proxy as `test-viewer` (the visitors' account, whose dev password stays public), so the stand-in needs no secret file. Two checks beyond ADR-0097 §4's: **s12**, that browser login as `test-viewer` through the proxy with `U/oidc/callback` and PKCE (the authorization request must accept the redirect URI, the login form must post to `U/auth/…`, the login must redirect to `U/oidc/callback` with a code, the code must give a token with `iss = U/auth/realms/spillway`, and that token must get 200 from `/api/v1/me` through the proxy): the task asked for a check that a login redirect uses the stand-in URL; **s13**, that no throwaway password, rotated client secret or token (`eyJ…`) appears in anything the test printed. In s7, Keycloak's `admin-cli` tokens in realm spillway carry no realm roles (the client's scope), so "a token with `admin`" is checked as: the password grant with `DEMO_ADMIN_PASSWORD` succeeds and the admin API lists `admin` among `test-admin`'s realm role mappings; a refused password grant is `invalid_grant`, which Keycloak answers with 400 once brute-force detection is on (401 without), so both count as refused, while a refused client secret must be 401. s10's admin-ui part uses public endpoints only (an authorization request and a logout with `U`'s URIs answer 400; with `http://localhost:8888`'s, 200, and the logout 200 or its 302 to the URI), because after the stop the Keycloak admin password is compose's, which the script does not read. s11 watches `docker events` for every container created in the project during the test and fails if any has the cloudflared image.
7. **Stall tolerance (ADR-0026, ADR-0027, ADR-0034).** Every check reads configuration or a single answer, never a time or a rate: each request has a 15 s timeout, about 18 times the worst recorded stall (820 ms), and the services were recreated with `--wait` before the checks start. A stall can delay an answer but cannot change it, so the checks have no retry and no re-run rule.
8. **PromQL on the anonymous Grafana** (ADR-0104's deferred note): anonymous viewers can send any PromQL through `/grafana/api/ds/query`. ADR-0096/0097/0104 set no query-cost or timeout limit, so this task adds none; it is listed for the user (options: the datasource's `timeout`/`queryTimeout` in the demo provisioning, Prometheus's `--query.timeout`/`--query.max-samples`, which would also change dev).

## Consequences

- `make demo-share-test` runs the share path end to end in about two minutes (127–128 s in three runs on this laptop, two Keycloak recreates included; ADR-0098 budgets 5) with no tunnel, network connection or secret; `make verify-m8` runs it (ADR-0098 part S) and prints s1–s13.
- `make demo` and `make demo-down` each recreate Keycloak once more than before (ADR-0104 §6's shortcut is gone).
- During a share, `make demo-reset` and `make demo` refuse; faults and scenarios work.
- The real tunnel's flags and the cloudflared container's read-only root filesystem are untested until the user's first `make demo-share`.

## Alternatives considered

- **The rotated secret in `share.env`** — every compose interpolation and any `docker compose config` would expand it; ADR-0097 keeps it in its own `0600` file.
- **s9b with a mounted secret file in the stand-in** — needs the file readable inside it; the visitors' login is what a tunnel request does anyway.
- **Polling checks until they pass** — the settings are static after the recreates; a poll would only hide a wrong setting that fixes itself.
- **Stopping the tunnel only in `make demo-down`** (instead of a full `make demo-share-stop`) — quicker, but ADR-0097 §3 says demo-down runs the stop.
