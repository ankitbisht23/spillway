# 0036. Control-plane data model, migrations and REST API

- **Status:** Accepted
- **Date:** 2026-11-13
- **Requirement IDs:** CP-01, CP-05, CP-10, CP-14, CP-19, CP-21, SEC-06, SEC-08, UI-05, UI-06

## Context

M5 adds the control plane: a Go binary over Postgres with a REST admin API (CP-10). The design gives a table of core tables with "key columns", an admin API table, and fixes the stack (pgx, sqlc, goose, oapi-codegen, oasdiff). It leaves open:

- the exact tables, types, keys, constraints and indexes, and how entities get the stable IDs that Redis keys and identity references need (ADR-0017 used policy names until M5; the design says the control plane assigns stable IDs);
- how config entities are stored without a second copy of `config.proto` in SQL columns that drift from it (CP-21);
- how `controlplane migrate` runs, what "backward compatible for one release" means in practice (CP-19), and what M5 does about the Helm Job when there is no chart until M7;
- the REST conventions: resource shapes, errors, status codes, pagination, filtering, ETags and the `If-Match` rules (CP-14), and how the OpenAPI source, generated stubs and `oasdiff` fit together (CP-10);
- the control plane's process layout, settings and place in compose.

ADR-0037 covers publish, rollback and the identity path; ADR-0038 the Watch stream and the active replica; ADR-0039 and ADR-0040 authentication, RBAC, audit and secrets; ADR-0041 precedence, access lists and heavy hitters. This ADR owns the schema they all write to.

## Decision

### Binary, packages and dependencies

- `cmd/controlplane` with subcommands `serve` (the default), `migrate` and `healthcheck` (asks its own admin `/readyz`, like the gateway's). Packages: `internal/controlplane/store` (sqlc queries, migrations), `internal/controlplane/api` (REST handlers), `internal/controlplane/stream` (ConfigService, ADR-0038), `internal/auth` (token verification shared with the gateway, ADR-0039). Dockerfile target `controlplane`: distroless `nonroot`, read-only root filesystem (SEC-10), same base digest as the gateway.
- New Go modules, exact versions (each the newest release at least two weeks old today): `github.com/jackc/pgx/v5` **v5.12.0**; `github.com/pressly/goose/v3` **v3.29.0** (the library, same version as the pinned CLI); `github.com/oapi-codegen/runtime` **v1.8.0**; `github.com/getkin/kin-openapi` **v0.142.0** (what oapi-codegen v2.8.2's embedded spec needs); `github.com/testcontainers/testcontainers-go` and its `modules/postgres` **v0.44.0**. sqlc v1.31.1, goose v3.29.0, oapi-codegen v2.8.2 and oasdiff v1.35.0 are the tools `make tools` already pins. A version that `govulncheck` flags is raised to the oldest fixed release, recorded in the task's PR.
- Store tests (`test/integration`, build tag `integration`) run against a Postgres 18.6 testcontainer, the same image as compose, with a fresh database per test package (design, Testing).

### IDs and names

- Every entity has `id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`. IDs are never reused (the identity sequence only moves forward). `BY DEFAULT` lets a rollback (ADR-0037) put rows back under their own IDs.
- IDs are JSON integers in the REST API and `int64` in `config.proto`. Where a string ID is needed (Redis key parts, hash tags), it is the decimal form: managed mode's Redis keys are `rl:v1:{t:<tenant id>}:<policy id>:…`. In static mode the policy and tenant names keep that role (ADR-0017, ADR-0021). Moving a deployment from static to managed config resets counters once, as the design's Redis keys section already says.
- Names: `text NOT NULL CHECK (name ~ '^[A-Za-z0-9._-]{1,64}$')`, unique per table (consumers: unique per tenant). Config entities refer to each other by name inside a config (as in YAML and the proto); identity refers to config by ID (a rename keeps the reference).

### Tables

Config entities store one `spec jsonb` column: the protojson form (proto field names) of the entity's `config.proto` message without the fields that have their own columns. The column is written only after `protojson.Unmarshal` into that message (with `DiscardUnknown: false`) succeeds, so a stored spec always parses. Columns exist only for what is keyed, referenced, constrained or indexed. This is a change from the design table's per-field "key columns" (`match`, `strip_prefix`, `transforms`, … as columns): with one `spec`, a field added to the proto (`lease_k` in M7) needs no migration and cannot drift from CP-21's one schema.

Every mutable table has `version bigint NOT NULL` (CP-14): for config tables the working-set revision at the row's last change, for identity tables the identity version at its last change (ADR-0037). Both counters only grow, so a row deleted and created again never repeats an ETag. Every table has `created_at` and `updated_at` (`timestamptz NOT NULL DEFAULT clock_timestamp()`).

`replica_versions` and `heavy_hitters` are pruned after 7 days (CP-22, ADR-0038, ADR-0041). `audit_log` is append-only (ADR-0040). `quota_usage` arrives with RL-10 in M7. The identity change history is `audit_log` rows with `identity_version` set, so there is no separate identity-changes table.

**Every query path uses an index.** Lists are keyset scans of the PK or of a listed index; lookups go by PK, a unique name or a listed index; FK cascades and "still in use" checks use the indexes named above (`tenants(plan_id)`, `consumers(plan_id)`, `overrides(policy_id)`, `api_keys(consumer_id, id)`, …). The only full-table reads are intended ones: validate, publish, rollback and export read the whole config working set, and the identity snapshot (ADR-0037) reads every identity table. Each sqlc query file states the index it relies on in a comment, and the schema-api task adds a test that runs `EXPLAIN` for every named sqlc query with `SET enable_seqscan = off` (so the planner picks an index whenever one can serve the query, however small the table) and fails on a `Seq Scan` outside the whole-table reads listed here.

### Migrations (CP-19)

- SQL files in `internal/controlplane/store/migrations/NNNNN_name.sql`, embedded in the binary, run by the goose library with Postgres's session advisory lock (goose's `WithSessionLocker`), so two `migrate` runs never interleave. Migrations are forward-only: no `-- +goose Down` sections; a bad migration is fixed by the next one.
- **`controlplane migrate`** connects as the owner role (`spillway`), applies pending migrations, then makes sure the app role `spillway_app` can log in with `SPILLWAY_CP_DATABASE_PASSWORD` (ADR-0040), prints each applied version and exits 0. It is idempotent: a second run applies nothing and exits 0.
- **`controlplane serve`** never migrates. At start it reads goose's version table and stops with `database schema <n> is older than this binary needs (<m>): run controlplane migrate` when it is behind. A newer schema is accepted (a rolling deploy runs the old binary on the expanded schema).
- **Compose**: a one-shot service `migrate` (the `controlplane` image, `command: ["migrate"]`, label `spillway.oneshot: "true"` so `make verify-m0` expects exit 0, `depends_on: postgres: service_healthy`) and the long-running `controlplane` with `depends_on: migrate: { condition: service_completed_successfully }`. This is the `migrate` service ADR-0004 and the M0 checklist already name.
- **Expand, then contract** (one release of compatibility). The schema after release N's migrations must still serve release N−1's binary, which is still running during N's rollout. So a release may add (nullable columns, columns with defaults, tables, indexes — large ones with `CREATE INDEX CONCURRENTLY` in a `-- +goose NO TRANSACTION` file) but may drop, rename or narrow only what the previous release's binary no longer uses. Worked example, renaming `consumers.name` to `display_name`:
  1. **Release N (expand).** Migration: add `display_name text`, backfill it from `name`, and a trigger that, on insert or update, fills whichever of the two the writer left unchanged from the other (N−1 writes `name`; N writes `display_name`). Binary N reads and writes `display_name` only.
  2. **Release N+1 (contract).** Migration: drop the trigger, then drop `name` and add `NOT NULL` and the unique index to `display_name`. The binary still running during this rollout is N, which never touches `name`.
  
  Writing both columns from binary N would be wrong: N+1's contract would then break N's writes mid-rollout. PRs that change the schema state in their description which release may contract what.
- **Helm.** The chart arrives in M7 (no `deploy/helm` exists yet). The contract it must meet is fixed here: a `pre-install,pre-upgrade` hook Job running the `controlplane` image with `migrate`, the owner credentials from a Secret, `backoffLimit: 0` and `hook-delete-policy: before-hook-creation`; the Deployment does not start a new binary until the Job succeeds. ADR-0035 says how the M5 checklist box treats this.

### REST API (CP-10, CP-14)

**Source and generation.** `api/openapi.yaml` (OpenAPI 3.0.3) is the source. oapi-codegen v2.8.2 with `api/oapi-codegen.yaml` generates `internal/gen/apiv1/apiv1.gen.go`: models, a `net/http` (Go 1.22 `ServeMux`) server, the strict server interface and the embedded spec. The generated file is committed, like `internal/gen/configpb`. New Makefile targets: `make api` regenerates; `make lint-api` (part of `make lint`) regenerates into a temp directory and diffs it against `internal/gen/apiv1` (`internal/gen/apiv1 is stale: run make api`), then runs `oasdiff breaking --fail-on ERR` against `origin/main:api/openapi.yaml`, skipped with a message while main has no spec (as `lint-proto` did for `buf breaking`). CI's go job runs it in a step named "OpenAPI: generated code, oasdiff breaking (CP-10)". The UI client (UI-05) is generated from the same file in M6. Every operation has an `operationId` and an `x-spillway-roles` list (ADR-0040).

**Proto parity.** Config entity schemas use the proto's field names. A unit test walks every config entity schema in the spec and the matching proto message descriptor and fails on any field present in one and not the other, except the REST-only `version`, `created_at` and `updated_at` (ADR-0005's M5 test).

**Format.**

- JSON bodies, `Content-Type: application/json` (import and export: `application/yaml`). Field names are snake_case. Times are RFC 3339 in UTC; durations are Go duration strings, as in YAML (ADR-0005). Integers, `int64` fields included, are JSON numbers.
- Requests are decoded strictly: an unknown field is 400, so a typo is never silently dropped. Bodies are capped at 1 MiB (import: 10 MiB); larger is 413.
- `X-Request-Id` is propagated or generated, as by the gateway (ADR-0013), returned on every response, and stored in audit records.
- `PUT` replaces the whole entity; there is no `PATCH`. `POST` to a collection creates and answers **201** with `Location` and `ETag`. `DELETE` answers **204**. Action endpoints (`/drain`, `/rotate`, `/revoke`, `/publish`, `/rollback`, `/import`) answer **200** with the resulting object.

**Resources (M5).** All under `/api/v1`. Each entity's JSON is its proto message's fields plus `id`, `version`, `created_at`, `updated_at`:

**Errors.** The gateway's error body is `{"error": "<message>"}` (ADR-0017); the control plane keeps that key and adds machine-readable fields:

```json
{"error": "validation failed", "code": "validation_failed", "request_id": "…",
 "details": [{"entity": "route", "id": 12, "name": "orders-api", "path": "upstream", "message": "upstream \"orders\" does not exist"}]}
```

| Status | `code` | When |
| --- | --- | --- |
| 400 | `invalid_request` | malformed JSON or YAML, unknown field, bad query parameter |
| 401 | `unauthenticated` | no, expired or invalid bearer token; with `WWW-Authenticate: Bearer` (ADR-0040) |
| 403 | `forbidden` | the token's roles do not allow the operation |
| 404 | `not_found` | no such entity or version |
| 409 | `conflict` | a unique name taken, an entity still referenced (a tenant with consumers), a state that forbids the action (rotating a revoked key), `nothing_to_publish` |
| 412 | `precondition_failed` | `If-Match` does not match; `details` carries the current version |
| 413 | `payload_too_large` | body over the cap |
| 415 | `unsupported_media_type` | wrong `Content-Type` |
| 422 | `validation_failed` | per-entity rules on create, update and import; CP-03 validation on publish and rollback; identity references to unpublished config |
| 428 | `precondition_required` | `If-Match` missing where required |
| 500 | `internal` | anything else; logged with the request ID, never echoed |
| 503 | `unavailable` | Postgres unreachable |

**ETags and `If-Match`** (CP-14). `GET` of an entity answers `ETag: "<version>"` (strong). `PUT` and `DELETE` require `If-Match` with that value: missing is **428**, different is **412**. The drain action requires `If-Match` with the upstream's ETag, as it changes the upstream. `POST /config/import`, `/config/publish` and `/config/versions/{v}/rollback` require `If-Match` with the working-set revision (`"<revision>"`, ADR-0037). Key rotation and revocation take no `If-Match`: they edit no fields, revocation is idempotent and must be one click (ADR-0039). `If-None-Match` and weak ETags are not supported.

**Pagination** (UI-06). Every list is cursor-paginated (keyset): `?limit=` (default 50, 1–500) and `?cursor=` (opaque: base64url of the last row's sort key). The answer is `{"items": [...], "next_cursor": "…" | null}`. Entities sort by `id` ascending; config versions by `version` descending; the audit log by `id` descending; heavy hitters by `denied + shadow_denied` descending over the requested range (at most 500, no cursor). Offset pagination was not chosen: `OFFSET` scans every skipped row, and the audit log only grows.

**Filtering.** Only exact-match query parameters on indexed columns, listed per operation in the spec: `?name=` on every named collection; consumers `?tenant_id=`; keys none (the path names the consumer); overrides `?consumer_id=`, `?policy_id=`; access lists `?action=`, `?subject_type=`; audit `?entity=` with optional `?entity_id=`, `?actor_sub=`, `?since=`, `?until=`; heavy hitters `?since=`, `?until=` (default the last 15 minutes, at most 7 days), `?policy_id=`. No free-text search.

## Consequences

- One `spec` column per config entity keeps CP-21's single schema: the proto decides the fields, protojson validates them, and adding a proto field never needs a migration. SQL cannot query inside a spec without an index, so nothing filters on spec fields.
- IDs are integers, so Redis keys in managed mode are shorter than with names, and renaming a policy or tenant keeps its counters.
- The control plane needs two Postgres roles and two passwords; `migrate` manages the app role's login, so compose and Helm only supply secrets.
- A breaking change to `api/openapi.yaml` fails `make lint`; a deliberate one needs a new `/api/v2` path, not an edit.
- Follow-up: M7's Helm chart implements the migrate Job contract above; M6 adds the shadow report, named metrics queries and SSE to the spec.

## Alternatives considered

- **One column per config field** (the design table's key columns) — a migration for every proto field and a second schema that can drift from `config.proto`.
- **UUIDs or text IDs** — longer Redis keys (NFR-10's 200 B per key) for no benefit; nothing outside one control plane mints IDs.
- **Names as the stable IDs** — a rename would reset counters and break identity references.
- **Foreign keys from identity to config tables** — a config delete in the working set would be blocked before publish, and a rollback could not reset the working tables.
- **Migrations run by `serve` at start** — two replicas would race, and CP-19 asks for a separate step.
- **Down migrations** — never run in a rolling deploy; fixing forward is the only path that keeps N−1 working.
- **Offset pagination** — scans grow with the offset; the audit log grows forever.
- **`PATCH` with JSON Merge Patch** — a second update path to validate and audit; `PUT` with `If-Match` is enough for a UI that always has the whole entity.
- **The REST API serving protojson directly** — `int64` fields would be JSON strings and the UI client would lose generated types.
