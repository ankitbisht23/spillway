# 0075. kind cluster, Helm chart and observability as code

- **Status:** Accepted
- **Date:** 2026-11-24
- **Requirement IDs:** GW-23, GW-25, GW-27, SEC-02, SEC-04, SEC-06, SEC-09, SEC-10, CP-07, CP-19, CP-22, OB-04, OB-05, OB-06, OB-08, NFR-14

## Context

M7 boxes 6 and 7 deploy Spillway with a Helm chart `spillway` (gateway + control plane) on a 3-node kind cluster `spillway`, with dependencies (Redis Cluster, Postgres, Keycloak, observability) as plain manifests in `deploy/kind/` using compose's pinned images, Keycloak on HTTPS so issuer and JWKS URLs are `https://` (SEC-04), `make kind-up` / `make kind-down` always passing `--context kind-spillway`, dashboards, alert rules and runbooks as code (OB-04 – OB-06, OB-08); the gateway is the edge (NodePort + `extraPortMappings` on `127.0.0.1:443`, no port 80, no plain HTTP), with a preStop delay and `maxUnavailable: 0`, admin ports on the pod IP behind a NetworkPolicy admitting Prometheus and the kubelet (GW-25), kind ranges in the upstream allow-list (SEC-06), the control plane at `replicas: 1`, and the gateway snapshot on a writable volume with a runbook for emptyDir (CP-07). NFR-14 needs zero failed requests during a rolling restart under load on kind.

Constraints: docs/setup.md Step 6 puts the cluster in its own kubeconfig, `~/.kube/spillway-kind`; the host's kind (v0.33.0) and helm (v4.3.1) are Homebrew builds; Docker Desktop has about 8.3 GB; ADR-0040 and ADR-0047 left **P10** to M7: the stream's client certificate name is the replica name (D7 of M5), which a Deployment's pods cannot each have; and M5 deferred the CP-07 runbook and its Helm parts, and the Helm parts of CP-19 (migrate Job) and SEC-02 (certs from a Secret).

## Decision

### D10. The kind cluster

- **Pinned tools.** `make tools` gains `kind` through the existing `tool` macro (`go install sigs.k8s.io/kind@v0.33.0`, the host's version on 2026-11-24), and `helm` (v4.3.1) and `kubectl` as official release binaries downloaded into `./bin` by a new `download-tool` macro that checks each file against a SHA-256 committed in the Makefile per platform (darwin-arm64, darwin-amd64, linux-amd64, linux-arm64), with the same stamp files. `kubectl`'s version is the newest patch, released at least two weeks before the kind task, of the node image's Kubernetes minor. The Makefile never calls the Homebrew binaries.
- **Node image.** The newest Kubernetes minor for which kind v0.33.0's release notes list a node image, pinned in `deploy/kind/cluster.yaml` as `kindest/node:<version>@sha256:<digest>` exactly as those notes give it.
- **Cluster** (`deploy/kind/cluster.yaml`): name `spillway`; one control-plane node and two workers; `networking.podSubnet: 10.244.0.0/16`, `serviceSubnet: 10.96.0.0/16` (kind's defaults, written out because SEC-06's allow-list names them); kindnet with its network-policy support (kind ≥ 0.24), so NetworkPolicies are enforced; on the control-plane node `extraPortMappings: [{containerPort: 30443, hostPort: 443, listenAddress: 127.0.0.1, protocol: TCP}]`, and nothing else on the host.
- **Context discipline.** The Makefile sets `export KUBECONFIG := $(HOME)/.kube/spillway-kind`, runs kind as `$(BIN)/kind … --name spillway --kubeconfig $(KUBECONFIG)`, kubectl as `$(BIN)/kubectl --context kind-spillway` and helm as `$(BIN)/helm --kube-context kind-spillway`, in every target and script (`test/kind/*.sh` take the same variables). kind writes only that file; `~/.kube/config` and any current context are never touched.
- **Namespaces:** `spillway` (the chart), `spillway-deps` (Redis, Postgres, Keycloak, the demo upstream), `spillway-obs` (observability).
- **Dependencies** (plain manifests, `deploy/kind/deps/*.yaml` and `deploy/kind/obs/*.yaml`, applied with `kubectl apply -f`), with compose's images and tags (digests come at release, ADR-0076):
  - Redis Cluster: `redis:8.10.3`, a StatefulSet `redis` of 6 pods with a headless Service, `cluster-announce-hostname redis-N.redis.spillway-deps.svc.cluster.local`, `cluster-preferred-endpoint-type hostname`, compose's settings (no persistence, `cluster-node-timeout 3000`, `maxmemory 256mb`, `noeviction`), and **`requirepass` / `masterauth`** from a Secret (ADR-0040 left the Redis password to Helm); a Job `redis-init` creates the cluster.
  - Postgres: `postgres:18.6`, a StatefulSet of 1 with a 1 Gi PVC on kind's default `standard` storage class.
  - Keycloak: `quay.io/keycloak/keycloak:26.8.1` serving **HTTPS only** on 8443 (`KC_HTTP_ENABLED=false`, `KC_HTTPS_CERTIFICATE_FILE` / `_KEY_FILE` from a Secret), `KC_HOSTNAME=https://keycloak.spillway-deps.svc.cluster.local:8443/auth`, `KC_HTTP_RELATIVE_PATH=/auth`, the realm imported from `deploy/compose/keycloak/realm.json` (a ConfigMap), health on its management port. So the issuer and JWKS URLs the gateway and control plane use are `https://keycloak.spillway-deps.svc.cluster.local:8443/auth/realms/spillway…`, and they run without `dev_mode` (SEC-04).
  - Demo upstream: `mccutchen/go-httpbin:2.26.0`, a Deployment of 2 with HTTP probes (compose's busybox healthcheck layer is not needed).
  - Observability: Prometheus `v3.15.1` (Kubernetes service discovery limited to the `spillway` namespace through a Role, a `replica` label relabelled from the pod name so ADR-0059's per-replica queries work, `--enable-feature=exemplar-storage`, the rule files below), Grafana `13.3.0` (datasources and the dashboards below from ConfigMaps), Loki `3.7.9`, Tempo `3.0.0`, OTel Collector contrib `0.164.0`, and `oliver006/redis_exporter` (new; the newest release at least two weeks old, pinned exactly; also added to compose for the Redis dashboard and alert).
- **Certificates and Secrets.** `make certs` gains, in the gitignored directories: `deploy/certs/kind-gateway.pem` (names `localhost`, `127.0.0.1`, `spillway-gateway`, `spillway-gateway.spillway.svc`, `spillway-gateway.spillway.svc.cluster.local`), `deploy/certs/kind-keycloak.pem` (the Keycloak names above), and in `deploy/stream-certs/kind/` a control-plane server certificate (`spillway-controlplane`, `spillway-controlplane.spillway.svc`, `….cluster.local`) and one fleet client certificate named `spillway-gateway` (P10 below), from the existing stream CA. `make kind-up` creates every Secret from those files and from `deploy/kind/dev-secrets.env` (committed; every value `dev-only-not-secret`, already allowlisted, so `.gitleaks.toml` is unchanged) only by reference, `kubectl create secret … --from-file / --from-env-file --dry-run=client -o yaml | kubectl apply -f -`, never echoing a value; the mkcert CA's public certificate goes into a ConfigMap the same way. Nothing reads `.env.local` or `.env.demo`.
- **Images.** `make kind-images` builds the root Dockerfile's `gateway`, `controlplane`, `loadgen` and `chaos` targets for the host's platform (`docker buildx build --load`), tagged `spillway-<name>:kind`, and runs `kind load docker-image … --name spillway`; the chart uses them with `imagePullPolicy: Never`. No local registry. Third-party images are pulled by the nodes.
- **Memory plan** (limits; requests are half): kind's own control plane and kubelets about 1.2 GB; Keycloak 768 Mi (`-Xmx512m`); Prometheus 512 Mi; Postgres, Grafana, Loki, Tempo, the control plane 256 Mi each; three gateways 256 Mi each; OTel Collector 192 Mi; six Redis nodes 64 Mi each; redis_exporter, two upstreams 64 Mi each; a loadgen Job 256 Mi. About **5.5 GB** in all, which fits in 8.3 GB only with compose stopped. `make kind-up` refuses to start while containers of the `spillway` compose project are running ("run `docker compose down` first; kind and compose do not fit together in 8.3 GB"); `make kind-down` does not restart compose (`make dev` does). Containers of other projects are left alone.
- **Targets.** `make kind-up` (creates the cluster if absent, Secrets and ConfigMaps, dependencies and waits for them, images, `helm upgrade --install spillway deploy/helm/spillway -n spillway -f deploy/kind/values.yaml --wait --timeout 10m`; about 10 minutes from nothing), `make kind-down` (`kind delete cluster --name spillway` and removes the kubeconfig file), `make kind-smoke`, `make kind-grafana` and `make kind-prometheus` (port-forwards on 127.0.0.1:13000 and 127.0.0.1:19091, docs/ports.md).
- **Smoke test** (`make kind-smoke`, `test/kind/smoke.sh` plus a Job running `chaos kindsmoke` in the `spillway` namespace; at most 3 minutes; PASS/FAIL lines): three nodes Ready; every pod in the three namespaces Ready; Redis `cluster_state:ok` (via `redis-cli` in a Redis pod, the password from the pod's own environment, never printed); from the Job: Keycloak discovery over HTTPS with `issuer` equal to the https URL and its JWKS reachable; `GET https://spillway-gateway.spillway.svc/bytes/16` → 200; the control plane's `/readyz` → 200; the gateway's admin port **not** reachable from the Job's pod (connect times out in 2 s: the NetworkPolicy works); Prometheus's targets for every gateway and the control plane `up`; from the host, `https://127.0.0.1:443/bytes/16` → 200 with the mkcert CA and nothing listening on 127.0.0.1:80. Before the chart exists (between the kind and helm tasks) it checks the dependency lines only.

### D11. The Helm chart `spillway`

`deploy/helm/spillway/` (gateway + control plane only; dependencies are D10's manifests). `values.yaml` holds production-shaped defaults; `deploy/kind/values.yaml` the kind overrides. `make lint` gains `lint-helm`: `helm lint` and `helm template` with both values files.

- **Gateway.** A Deployment, `replicas: 3` in kind values; `strategy: RollingUpdate, maxSurge: 1, maxUnavailable: 0`; `lifecycle.preStop.sleep.seconds: 10` (the kubelet's sleep action, so the distroless image needs no shell); `terminationGracePeriodSeconds: 45` (10 s preStop + `SPILLWAY_GATEWAY_DRAIN` 5 s + `SPILLWAY_GATEWAY_SHUTDOWN_GRACE` 15 s, both at their defaults, + 15 s slack; GW-23). TLS traffic on container port 8443 only; `SPILLWAY_GATEWAY_HTTP_ADDR` is never set (no plain HTTP, SEC-01). Admin on `$(POD_IP):8001` from the downward API (GW-25). Readiness `GET /readyz` on 8001 every 2 s, failure threshold 1; liveness `GET /healthz` every 10 s, failure threshold 3. `GOMAXPROCS` and `GOMEMLIMIT` follow the limits as today (GW-27).
- **Edge.** A Service `spillway-gateway`, `type: NodePort`, port 443 → 8443, `nodePort: 30443`, `externalTrafficPolicy: Cluster`; no ingress controller, no port 80. Only 443 is exposed; the admin port is in no Service.
- **NetworkPolicies** (GW-25): the gateway's admits TCP 8443 from anywhere, and TCP 8001 only from pods labelled `app.kubernetes.io/name: prometheus` in namespace `spillway-obs` and from the node network (`networkPolicy.kubeletCIDRs`, which `make kind-up` sets from `docker network inspect kind`), the kubelet's probes coming from the node; the control plane's admits 9090 from the gateway pods, 8080 from pods in `spillway`, 8081 from Prometheus and the node network. Egress is not restricted in v1.
- **Upstream allow-list** (SEC-06): kind values set `SPILLWAY_GATEWAY_ALLOWED_NETWORKS` and `SPILLWAY_CP_ALLOWED_NETWORKS` to `10.244.0.0/16,10.96.0.0/16` (pods and Services); link-local and metadata stay rejected as always.
- **Control plane.** A Deployment with `replicas: 1` (CP-22), `RollingUpdate` with `maxSurge: 1`, `maxUnavailable: 0` (the new pod waits as a standby until the old one releases the active lock, ADR-0038); Service `spillway-controlplane` (ClusterIP: 8080 REST + UI, 9090 gRPC), admin on the pod IP; REST and UI internal (SEC-02; `kubectl port-forward` for a person). Settings: database, Redis (the quota flusher, ADR-0070), OIDC issuer and JWKS on https with the mkcert CA, Prometheus URL, heavy-hitter secret file, `SPILLWAY_CP_GRPC_FLEET_IDENTITIES` (below).
- **Migrations** (CP-19): a Job hook `pre-install,pre-upgrade` running `controlplane migrate` with the migrate role's settings, `hook-delete-policy: before-hook-creation,hook-succeeded`, `activeDeadlineSeconds: 300`.
- **Gateway identity in Kubernetes (P10 of M5):** a **fleet identity**. The control plane's new setting `SPILLWAY_CP_GRPC_FLEET_IDENTITIES` (comma-separated certificate names, default empty, so compose is unchanged) lists names that stand for a fleet: a client certificate whose single DNS name F is listed may watch and heartbeat as any replica ID that matches `^F-[a-z0-9-]+$` and is a DNS label (≤ 63 characters), and its requests must carry that `replica_id` (empty is `PERMISSION_DENIED` for a fleet certificate). The gateway's new setting `SPILLWAY_GATEWAY_REPLICA_ID` (Helm sets it to the pod name from the downward API; pod names start with `spillway-gateway-`) names the replica when set, and must start with `<certificate name>-` or the gateway refuses to start; unset, the certificate's name is the replica name as today. All gateway pods mount one Secret with the fleet certificate `spillway-gateway`. Tests: the interceptor's rules (listed name, prefix, label, empty ID), the gateway's start check, and an integration test with two replica IDs on one fleet certificate.
- **Snapshot volume** (CP-07): an `emptyDir` (`sizeLimit: 64Mi`) at `/var/lib/spillway`, `SPILLWAY_GATEWAY_SNAPSHOT` pointing into it, the root filesystem read-only (SEC-10). **CP-07's Helm parts:** a PodDisruptionBudget (`maxUnavailable: 1`), so voluntary evictions never take every snapshotted pod at once; and an optional seed: with `gateway.snapshotSeed.secretName` set, an init container copies `snapshot.pb` from that Secret into the empty volume using a new subcommand `gateway snapshot-seed --from <file> --to <file>` (it checks the file parses and its schema major, and does nothing when the target exists). A second new subcommand, `gateway snapshot-export`, writes a running pod's snapshot to stdout (`kubectl exec`), since the distroless image has no `tar` for `kubectl cp`.
- **Runbook** `docs/runbooks/gateway-snapshot.md` (CP-07): a replacement gateway pod started while the control plane is unreachable has no snapshot in its new emptyDir and stays unready (log line `no snapshot and no control plane`); first checks (control plane pod and Postgres, `gw_config_sync_age_seconds` on the others); mitigation: restore the control plane (preferred, nothing else needed; ADR-0055: no restore-specific step after a database restore), or seed: export a live pod's snapshot into a Secret (`kubectl exec … -- /gateway snapshot-export | kubectl create secret generic spillway-gateway-seed --from-file=snapshot.pb=/dev/stdin`), set `gateway.snapshotSeed.secretName`, upgrade; and delete the seed Secret once the control plane is back (it holds API key hashes).
- **Pod security** (both workloads and the Job): `runAsNonRoot: true`, `runAsUser: 65532`, `runAsGroup: 65532`, `fsGroup: 65532`, `seccompProfile: RuntimeDefault`; containers `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, `capabilities: {drop: [ALL]}`; resource requests and limits from D10's plan.
- **Service accounts:** one each for the gateway, the control plane and the migrate Job, with `automountServiceAccountToken: false` and no Role (none of them calls the Kubernetes API).
- **Secrets by reference only:** values name existing Secrets (`gateway.tls.secretName`, `gateway.stream.secretName`, `controlplane.stream.secretName`, `heavyHitter.secretName`, `database.secretName`, `redis.secretName`, `oidc.caConfigMap`), mounted as files and passed as `X_FILE` settings (SEC-09). The chart never renders a secret value and has no secret values in its values files.

### Observability as code (OB-04, OB-05, OB-06, OB-08)

- **Dashboards** (OB-04): `deploy/grafana/dashboards/{overview,rate-limiting,upstreams,redis,control-plane}.json` (Grafana 13 schema), provisioned in compose (replacing nothing; compose's provisioning mounts the directory) and in kind (ConfigMaps). Overview: RPS, status mix, 429 rate, p50/p99 per route and tenant, availability SLI and burn; Rate limiting: decisions per policy and mode, deny cache, leases, quota decisions, Redis check latency; Upstreams: per-upstream latency, retries, circuit state, endpoint health and ejection; Redis: gateway-side errors and check latency plus redis_exporter's memory, ops and clients per node; Control plane: Watch streams, propagation (replica versions), quota flushes, SSE stream metrics, active replica.
- **Alert rules** (OB-05): `deploy/prometheus/rules/spillway.yaml`, loaded by compose's and kind's Prometheus. Availability SLO 99.9% over 30 days with the NFR-11 SLI; latency SLO 99% of requests within 0.5 s (`gw_request_duration_seconds_bucket{le="0.5"}`). Multi-window burn-rate alerts for each SLO: **fast** (burn > 14.4 over 1 h and over 5 m, severity page) and **slow** (burn > 6 over 6 h and over 30 m, severity ticket): `SpillwayAvailabilityBurnFast`, `…BurnSlow`, `SpillwayLatencyBurnFast`, `…BurnSlow`. `SpillwayRedisErrors`: `rate(gw_redis_errors_total[5m])` over `rate(gw_ratelimit_check_duration_seconds_count{backend="redis"}[5m])` > 1% for 5 m. `SpillwayRedisMemoryHigh`: redis_exporter's `used_memory / maxmemory` > 0.8 for 5 m (ADR-0034's note). `SpillwayConfigSyncStale`: `gw_config_sync_age_seconds > 60` (no `for`). `SpillwayCircuitOpen`: `gw_circuit_state == 1` for 5 m. Each has a `runbook_url` annotation to its file on `main` on GitHub. No Alertmanager in v1: Prometheus and Grafana show firing alerts.
- **Exemplars** (OB-06): the gateway's `gw_request_duration_seconds` and `gw_upstream_duration_seconds` observations carry an exemplar `{trace_id="<32 hex>"}` only when the request's span is sampled; the admin port serves OpenMetrics so they are exposed; Prometheus runs with `exemplar-storage` in compose and kind; Grafana's Prometheus datasource links exemplar trace IDs to Tempo.
- **Runbooks** (OB-08): `docs/runbooks/README.md` (an index) and one file per alert (`availability-burn.md` for both availability alerts, `latency-burn.md`, `redis-errors.md`, `redis-memory.md`, `config-sync-stale.md`, `circuit-open.md`), plus `gateway-snapshot.md`; each with **What it means**, **First checks** and **Mitigation**.
- **Tests** (`test/obs/obs_test.go`, plain Go): every dashboard parses, and every metric name in its queries and in the rules exists in the code's registrations or in redis_exporter's documented set; every alert has a `runbook_url` whose file exists; `make lint-obs` runs `promtool check rules` from the pinned Prometheus image (CI's integration job runs it). Unit tests for exemplars on sampled and unsampled requests; an integration test reads an exemplar back from compose Prometheus.

### NFR-14 on kind

`test/kind/rollout.sh` (run by verify-m7 and by the helm task): a Job running `loadgen` from inside the cluster against `https://spillway-gateway.spillway.svc/bytes/1024` (the NodePort Service's ClusterIP: the same Service, endpoints and pod lifecycle as the edge, without Docker Desktop's port forwarding in the measurement), trusting the mkcert CA, 300 rps, `-warmup 0`, 4 minutes, 50 connections, 10 s timeout. At +60 s: `kubectl --context kind-spillway -n spillway rollout restart deployment/spillway-gateway`, then `rollout status --timeout 5m`. **Failed** = any request with a transport error, a timeout or a non-2xx status, warm-up included (loadgen's `failures`, ADR-0034). **Pass:** zero failed requests, ≥ 99% of the target sent, the rollout complete within 5 minutes with three new pods Ready and every old pod gone before the load ends. Run at least three times by the helm task.

## Consequences

- One command builds a production-shaped deployment on the laptop, with HTTPS-only identity, NetworkPolicies and pod hardening, at the cost of stopping compose while it runs.
- Gateways in Kubernetes share one fleet certificate, so a stolen copy can act as any replica of that fleet (it could already read the full config as one replica); compose keeps one certificate per replica. Rollouts leave old pod names in the `replicas` table until they age out of `live_replicas`.
- The admin UI on kind is reachable with `kubectl port-forward`, but a browser login needs Keycloak's in-cluster https name, which the laptop does not resolve; interactive UI use stays on compose (and M8's demo), while kind checks the control plane with service tokens.
- On kind, client IPs reaching the edge are node IPs (SNAT with `externalTrafficPolicy: Cluster`), so IP-keyed limits see few addresses there.
- New tools in `./bin` (kind, helm, kubectl), new images (redis_exporter), new gateway subcommands (`snapshot-seed`, `snapshot-export`) and settings (`SPILLWAY_GATEWAY_REPLICA_ID`, `SPILLWAY_CP_GRPC_FLEET_IDENTITIES`).
- P28 adds the repository layout entries (`deploy/kind/`, `deploy/helm/spillway/`, `deploy/grafana/dashboards/`, `deploy/prometheus/rules/`, `docs/runbooks/`, `test/kind/`, `test/obs/`).

## Alternatives considered

- **A StatefulSet with one Secret per ordinal (P10's other option)** — keeps D7 as is, but a StatefulSet cannot surge, so `maxUnavailable: 0` (the design's box) is impossible and capacity drops by a pod during every restart.
- **cert-manager issuing a certificate per pod** — a cluster-wide dependency and its CRDs for one name per pod; heavier than the fleet rule.
- **An init container minting per-pod certificates from the CA** — every gateway pod would hold the CA key and could mint any identity, which is worse.
- **A local registry for images** — `kind load` is enough for three images on one machine.
- **The Homebrew kind and helm** — unpinned; `make tools` pins every other tool.
- **An ingress controller** — the gateway is the edge (design, Stack row).
- **Dashboards inside the Helm chart** — the chart cannot read files outside its directory, and compose needs the same files; Grafana is a kind dependency, not part of the chart.
- **Alertmanager** — no receivers in a laptop deployment; rules and runbooks are what OB-05 and OB-08 ask for.
