# 0086. Helm chart: implementation details

- **Status:** Accepted
- **Date:** 2026-11-26
- **Requirement IDs:** GW-25, SEC-02, SEC-04, SEC-06, SEC-09, SEC-10, CP-07, CP-19, CP-22, NFR-14

## Context

ADR-0075 §D11 sets the Helm chart `spillway` (gateway + control plane), the fleet identity for gateways in Kubernetes (M5's P10), the NetworkPolicies of GW-25, the migrate hook Job (CP-19), the snapshot volume, PodDisruptionBudget, seed and runbook (CP-07), pod hardening, token-less service accounts, Secrets by reference, and NFR-14 as an in-cluster load through a rolling restart. ADR-0085 built the cluster and named the Secrets, ConfigMaps and Prometheus discovery the chart builds on. Under T4 the observability bullets (dashboards, alert rules, exemplars, alert runbooks: OB-04, OB-05, OB-06, OB-08) are the next task's. This ADR records what ADR-0075 left open, where the implementation differs from its text, and the measured results. No requirement text changes.

## Decision

### The chart

1. **Fixed names.** Objects are `spillway-gateway`, `spillway-controlplane` and `spillway-migrate`, not prefixed with the release name: the fleet certificate is named `spillway-gateway`, pod names (the replica IDs) must start with it, and kind's Prometheus selects pods by `app.kubernetes.io/name`. One release per namespace; `values.yaml` says so.
2. **Required values.** `values.yaml` holds production-shaped defaults, but the values with no safe default (`gateway.allowedNetworks`, `controlplane.allowedNetworks`, `controlplane.database.url`, `controlplane.migrate.url`, `controlplane.oidc.issuer` and `jwksURL`, `networkPolicy.kubeletCIDRs`) fail rendering when empty, so a deployment cannot silently run without an allow-list or with probes the NetworkPolicy drops. `controlplane.replicas` other than 1 fails rendering (CP-22).
3. **`make lint-helm`** (part of `make lint`, and a step of CI's `go` job): `helm lint --strict` and `helm template` with the chart's `values.yaml` under `deploy/kind/values.yaml` (ADR-0075's "both values files"; the defaults alone do not render, by item 2, which a test checks), then `test/kind/helm_test.go` on the rendered manifests with the pinned helm (`SPILLWAY_HELM`, so they never skip there; a bare `go test` uses `bin/helm` if present and skips otherwise). The tests check, on the exact field paths: every pod's security context (non-root 65532, `RuntimeDefault` seccomp, no token, no privilege escalation, read-only root, `drop: [ALL]`), memory request = half the limit, no Secret object and no Role rendered, no `*PASSWORD*` / `*SECRET*` variable other than `_FILE`; the gateway's strategy (surge 1, unavailable 0), preStop sleep 10 s, grace 45 s, probes on `admin`, `$(POD_IP):8001`, replica ID from the pod name, the 64 Mi emptyDir, kind's ranges, no `HTTP_ADDR`, `DEV_MODE`, static config or address map; the edge Service (NodePort, only 443 → `https`, 30443, `Cluster`) and that no Service reaches an admin port or port 80; the PDB; the seed init container; the control plane (one replica, fleet identity, https OIDC with the CA, the flusher's Redis, ClusterIP); the migrate hook; each NetworkPolicy rule. **kubeconform is not used**: its default schemas are fetched at run time from an unpinned branch and do not cover Kubernetes 1.37; the field-path tests above and the real install on kind (server-side validation) cover what it would.
4. **Pod details** beyond ADR-0075: `enableServiceLinks: false` and `privileged: false` on every pod and container; the gateway's readiness probe has `timeoutSeconds: 2` (ADR-0075 gives period 2 s and threshold 1; the default 1 s timeout would let a host stall of 0.8 s plus a slow answer take a pod out, ADR-0034); the control plane's readiness has threshold 3 (ADR-0075 does not set it); no CPU limits, so GOMAXPROCS follows the node and the gateway is never throttled (GW-27 unchanged). The migrate Job has `backoffLimit: 1`.
5. **The migrate Job's service account is a hook** (`pre-install,pre-upgrade`, weight -10, `before-hook-creation`), because a pre-install hook runs before the release's own objects exist. Helm does not delete hook objects on uninstall, so it stays until the namespace or cluster goes (kind-down).
6. **Secrets as files.** Each secret key is mounted on its own as `…/value` with `defaultMode: 0440`; the pods' `fsGroup: 65532` makes them readable. The values name Secrets and keys only (`gateway.tls.secretName`, `gateway.stream.secretName`, `controlplane.stream.secretName`, `heavyHitter.secretName/key`, `controlplane.database`, `controlplane.migrate`, `gateway.redis`, `controlplane.redis`), and `oidc.caConfigMap` a ConfigMap.
7. **Carry items.** `controlplane.redis` sets `SPILLWAY_CP_REDIS_ADDRS`, `_USERNAME` and `_PASSWORD_FILE` (the quota flusher, RL-10); `gateway.maxConnectionsPerIP` sets `SPILLWAY_GATEWAY_MAX_CONNECTIONS_PER_IP` (1,024). With `externalTrafficPolicy: Cluster` the gateway sees node addresses (SNAT), so that cap and IP-keyed limits count per node; `values.yaml` notes it next to the Service and the cap (raise the cap, or list the node network in `trustedProxies`, when many clients share a node).

### New settings and subcommands

8. **Fleet identity** as ADR-0075 §D11: `mtls.FleetReplica(fleet, id)` (the fleet's name, `-`, at least one more character, a DNS label of at most 63) is the one rule; the control plane's `SPILLWAY_CP_GRPC_FLEET_IDENTITIES` (each name must be a DNS label) makes Watch and Heartbeat from a listed certificate require such a `replica_id` and use it as the replica name; an empty or foreign ID is `PERMISSION_DENIED` and logged (names only). The gateway's `SPILLWAY_GATEWAY_REPLICA_ID` (managed mode only) must pass the same rule against its certificate's name or the gateway does not start. Tests: the rule, both settings, and a gRPC test over mTLS with two replicas on one fleet certificate watching at once.
9. **`SPILLWAY_CP_OIDC_CA`** (new): ADR-0075 has the control plane fetch its JWKS over https "with the mkcert CA", but it had no setting for a CA; this mirrors the gateway's `SPILLWAY_GATEWAY_JWT_CA`, and both now use one helper, `auth.NewClientWithCA`.
10. **`gateway snapshot-seed --from --to`** does nothing when `--to` exists or `--from` does not (the seed Secret volume is `optional`, so pods still start after the Secret is deleted, as the runbook says to); a file that does not parse, lacks a section or has another schema major is an error and nothing is written. **`gateway snapshot-export [--from]`** checks the snapshot like the gateway would and writes it to stdout. Neither prints the content (API key hashes); tests check both.

### kind

11. **Install flow** (`make kind-up`): after the dependencies, `helm upgrade --install spillway … -f deploy/kind/values.yaml --set-json networkPolicy.kubeletCIDRs=[<kind network's IPv4 subnet>] --timeout 10m` with Helm 4's default `hookOnly` wait (it waits for the migrate Job only), then `rollout status` of the control plane, then the Job **`kind-seed`** (`chaos kindseed`, `deploy/kind/seed-job.yaml`), then `rollout status` of the gateways. ADR-0075 wrote `--wait`, but a managed gateway is not ready before its first config (ADR-0038), so waiting for every Deployment before anything is published would never finish. `chaos kindseed` imports and publishes `deploy/kind/config.yaml` (one upstream, go-httpbin in `spillway-deps`, route `/`, no auth, no policy) through the REST API with a `spillway-ci` service token from Keycloak over HTTPS, trusting only the mkcert CA; a 409 is "already current"; it tries again every 2 s for up to 150 s while the control plane cannot answer yet. Its client secret is the new key **`SPILLWAY_CI_CLIENT_SECRET`** in `deploy/kind/dev-secrets.env` (the realm's dev value `dev-only-not-secret`, already allowlisted), mounted as a file.
12. **Kubelet network.** `make kind-up` reads the IPv4 subnet of Docker's `kind` network (172.20.0.0/16 on this laptop) for `networkPolicy.kubeletCIDRs`. Measured: kindnet enforces the policies, and the kubelet's probes on the admin ports pass with only that block admitted.
13. **Smoke test** (ADR-0075 §D10's lines, ADR-0085 item 15 plus): the gateway and control-plane Deployments ready (control plane at 1 replica); from the Job, a request through `https://spillway-gateway.spillway.svc/bytes/16`, each admin address (every gateway pod's IP:8001 and the control plane's IP:8081, filled into the Job by `smoke.sh`) not accepting a connection within 2 s, and Prometheus's active targets of jobs `gateway` and `controlplane` all up and as many as the replicas; from the host, `https://127.0.0.1:443/bytes/16` → 200 with 16 bytes (curl with the mkcert CA, 10 s) and nothing on `127.0.0.1:80` (curl exit 7 or 28). **One difference from ADR-0075 §D10:** "the control plane's `/readyz` → 200" is checked through the kubelet (the Deployment's ready replica, whose readiness probe is `/readyz`), not from the Job, because the chart's NetworkPolicy closes the admin port to the Job by design; the Job instead checks that it is closed. The Prometheus line **waits** up to 45 s for discovery (a new pod is scraped within one 5 s interval of being discovered), polling every second; it is a wait for a condition, as `rollout status` is, not a re-run of a failed check. The Job's deadline is 100 s and the script waits 110 s; the whole test stays under 3 minutes (measured below).
14. **NFR-14** (`make kind-rollout`, `test/kind/rollout.sh`, `test/kind/rollout-job.yaml`) exactly as ADR-0075: loadgen in the cluster against the Service, 300 rps, no warm-up, 4 minutes, 50 connections, 10 s timeout, the mkcert CA; at +60 s `kubectl --context kind-spillway -n spillway rollout restart deployment/spillway-gateway` and `rollout status --timeout 5m`. PASS: loadgen's `failures` zero (transport errors, timeouts and non-2xx, warm-up included), achieved ≥ 99% of 300 rps, the rollout done within 5 minutes with every new pod Ready and none of the old names left, every old pod gone before +240 s. No retries. Stalls: no line measures latency; each request has 10 s and the time rules are minutes long, so a stall of up to ~0.8 s cannot fail a line by itself.
15. **Postgres and Redis on kind** speak plain TCP inside the cluster (`sslmode=disable`; compose's Redis settings), as the kind task deployed them; the chart has no default database URL, so a deployment chooses its own `sslmode`. The edge, Keycloak and the config stream are TLS.
16. **ADR-0085 item 10** (Redis pod limit 64 Mi under `maxmemory 256mb`): not hit in any run here (no OOM-kill, no restart of a Redis pod; nothing on kind writes many keys), so it is left for the review as ADR-0085 says.

### Boxes

17. This task ticks M7's **"kind specifics"** box (gateway as the edge, preStop and `maxUnavailable: 0`, admin ports behind a NetworkPolicy, kind ranges in the allow-list, control plane at `replicas: 1`, snapshot volume and emptyDir runbook). The **"Load tests against every NFR row"** box stays unticked: NFR-14 is now measured on kind, but NFR-02 is an open known limit by the user's decision (ADR-0084 §4), which says this box stays unticked. The **Helm chart / observability-as-code** box is the observability task's (T4).

## Measured

Filled in from the runs on 2026-11-26 (MacBook, Docker Desktop with 14 CPUs and ~8.3 GB; compose stopped first, as ADR-0085's memory plan needs):

- **Three full cycles** of `make kind-down` → `make kind-up` from nothing → `make kind-smoke` → `make kind-rollout`: all PASS (3 of 3). `make kind-up` 106, 139 and 136 s (the chart's part, from `helm upgrade` to the gateways ready, 10, 8 and 8 s; the seed published at once each time); `make kind-smoke` 12, 13 and 14 s; `make kind-down` 1, 1 and 2 s. On the first cluster, `make kind-up` again on the live cluster took 19 s and `make kind-smoke` 13 s (PASS).
- **NFR-14**, four valid runs, **4 of 4 PASS**, each with **0 failed of 72,000 requests** (all 2xx, no errors), 300 of 300 rps achieved, the rollout complete 3, 3, 5 and 4 s after the restart, every old pod gone at +78, +80, +82 and +80 s (the restart at +60 s; the load ends at +240 s); loadgen's p99 1.84, 1.98, 1.98 and 1.95 ms, max 39.9, 6.4, 7.5 and 17.5 ms (for information; NFR-14 has no latency rule). One earlier run had no verdict: the script's wait for the load Job ended before the load did and deleted the Job with its result (fixed: the wait now runs until 60 s past the load's end).
- **One run of `make kind-up` failed** before any of these, on the first try: the seed Job's pod had no `fsGroup`, so it could not read its 0440 secret file (fixed in `deploy/kind/seed-job.yaml`). And one `make kind-smoke` run started right after a manual `helm upgrade` failed its "pods Ready" line while old gateway pods were still terminating, as it should on an unsettled cluster; the same check passed once they were gone.
- **CP-07's seed path** on kind: `gateway snapshot-export` in a live pod (157 bytes, config and identity version 1) into the Secret `spillway-gateway-seed`, `helm upgrade --reuse-values --set gateway.snapshotSeed.secretName=spillway-gateway-seed`: each of the three new pods' init container logged `wrote /var/lib/spillway/snapshot.pb`; deleting the Secret and unsetting the value rolled the gateways back cleanly.
- No pod restarted in any run; Redis used about 3 MB per node (ADR-0085 item 10 not reached).

## Consequences

- `make kind-up` gives a working, production-shaped deployment: HTTPS-only edge on `127.0.0.1:443`, managed gateways with a fleet identity, a published demo config, NetworkPolicies that are enforced, and hardened pods with Secrets as files.
- A rolling restart of the gateways under load fails no request on kind (NFR-14).
- New settings: `SPILLWAY_CP_GRPC_FLEET_IDENTITIES`, `SPILLWAY_GATEWAY_REPLICA_ID`, `SPILLWAY_CP_OIDC_CA`; new subcommands `gateway snapshot-seed`, `gateway snapshot-export`, `chaos kindseed`; new targets `make lint-helm`, `make kind-rollout`; a new key in `deploy/kind/dev-secrets.env`.
- Re-running `make kind-up` on a live cluster does not restart pods whose `:kind` image changed (same tag, same spec); `kubectl --context kind-spillway -n spillway rollout restart` picks the new image up, or `make kind-down && make kind-up`.
- The migrate service account survives `helm uninstall` (a hook).

## Alternatives considered

- **`helm --wait` (watcher) with a post-install hook publishing the config** — Helm waits for every Deployment before post-install hooks, and the gateways are not ready before a config: a deadlock.
- **Release-prefixed names** — would need the fleet name, the certificate, Prometheus's selector and the smoke test to follow the release name, for a second release per namespace nobody needs.
- **kubeconform with pinned schemas vendored into the repo** — thousands of generated files for checks the field-path tests and the server already do.
- **Checking the control plane's `/readyz` from the Job by admitting the Job in the NetworkPolicy** — would weaken GW-25 for a test.
- **`SSL_CERT_FILE` instead of `SPILLWAY_CP_OIDC_CA`** — works with Go's loader but replaces the system roots and is implicit; the gateway already has an explicit setting.
