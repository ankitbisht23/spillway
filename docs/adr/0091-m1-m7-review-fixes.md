# 0091. M1–M7 review fixes

- **Status:** Accepted
- **Date:** 2026-11-27
- **Requirement IDs:** SEC-02, SEC-05, GW-25, GW-26, RL-04, RL-10, RL-18, RL-23, OB-02, OB-06, NFR-05

## Context

The M7 review read M1–M7 on `main` (6715255) through three lenses (security, correctness, requirements) and checked the carry items the M7 steps left for it. Some findings change what an accepted ADR says: the Helm chart's advice on `trustedProxies` (ADR-0086 item 7), who may reach the control plane's REST port (ADR-0075 §D11), and the hardening of the kind dependencies (ADR-0085 item 6). Others fill gaps that no ADR covers: a lease-served policy and its call's quotas (ADR-0069, ADR-0070, ADR-0077), and a quota override on a managed gateway without Redis (left open by the quotas task). Accepted ADRs are not edited, so the changes are recorded here. The rest of the findings are for the user and are listed at the end, with P-items where requirement text would change.

## Decision

### Edge and network

1. **`trustedProxies` never lists the node network** (SEC-05, RL-04; replaces ADR-0086 item 7's advice). With `externalTrafficPolicy: Cluster`, kube-proxy SNATs clients to node addresses and adds no `X-Forwarded-For`, because it works at L4. ADR-0086 suggested listing the node network in `trustedProxies` when many clients share a node. The gateway would then believe any `X-Forwarded-For` a client sends (`TrustedProxies.ClientIP`), so a client could choose the IP that IP-keyed limits, IP access lists and the per-IP connection cap see. `values.yaml` now says that `trustedProxies` lists only proxies that set or append `X-Forwarded-For`. It also says that real client addresses need `externalTrafficPolicy: Local`, with a gateway on every node that receives traffic, or an L7 proxy in front that is listed there. For many clients behind one node, the only advice left is to raise `maxConnectionsPerIP`. `test/kind/helm_test.go` checks that the kind install sets no `SPILLWAY_GATEWAY_TRUSTED_PROXIES`. The chart does not refuse a `trustedProxies` that overlaps `kubeletCIDRs`: Helm's template functions have no CIDR arithmetic, and comparing the strings would miss most overlaps while looking like a guard.
2. **The control plane's REST port refuses the gateway pods** (SEC-02, GW-25; changes ADR-0075 §D11's "its REST the pods of this namespace"). The rule for port 8080 now admits the namespace's pods whose `app.kubernetes.io/name` is not `spillway-gateway` (`matchExpressions … NotIn`). The gateways are internet-facing, and their kind upstream allow-list covers the Service range. Without this rule, an editor and a publisher could route the edge to `spillway-controlplane:8080` and put the admin API and UI on the public edge (still behind OIDC and RBAC). The gateways need only gRPC (9090). The seed Job and any other pod of the namespace keep REST. `TestChartNetworkPolicies` checks the rule.
3. **redis_exporter on kind gets a NetworkPolicy** (ingress and egress). The exporter applies `REDIS_PASSWORD` to every `/scrape?target=…` target, so any pod that could reach it could make it send the password to a host of its choosing. Egress is now limited to the Redis pods' 6379 in `spillway-deps` and to cluster DNS. Ingress is limited to Prometheus and to addresses outside kind's pod network (`0.0.0.0/0` except `10.244.0.0/16`). The second entry covers the kubelet's readiness probe, which comes from the node network that `make kind-up` learns only after the manifests are applied; every other pod is refused. `TestRedisExporterPolicy` checks the spec. **Not done:** `--redis.password-file`. It would need a JSON file holding the password, which `make kind-up` would have to build from the dev file, while Secrets are made only by reference. The egress rule already means that only the six Redis nodes can receive the AUTH. A default-deny policy for `spillway-deps` is also not added here. It is a larger change to every dependency's traffic and is left as a follow-up.
4. **Postgres on kind is hardened as far as its entrypoint allows** (refines ADR-0085 item 6). The pod has `seccompProfile: RuntimeDefault`, and the container has `allowPrivilegeEscalation: false` and `capabilities: { drop: [ALL], add: [CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETUID] }`. The image's entrypoint starts as root, takes the data and socket directories for `postgres` (chown, chmod) and drops to it with `gosu`. Those five capabilities are what that needs, and `gosu` is not a setuid binary, so no-new-privileges does not block it. The root filesystem stays writable, as ADR-0085 says. **`TestManifestHardening`** (new, `test/kind/kind_test.go`) checks every pod that deploy/kind and the kind Jobs run: `RuntimeDefault` seccomp, no privilege escalation, `drop: [ALL]`, no added capabilities, `runAsNonRoot` and a read-only root filesystem. It has an explicit exception list: Postgres runs as root first with the five capabilities and a writable filesystem, and Keycloak has a writable filesystem (it builds itself at start).

### Rate limiting

5. **A lease-served `fail_closed` policy still decides its call's quotas** (RL-10, RL-18, RL-23; fills a gap between ADR-0069 and ADR-0070). ADR-0070 makes a quota follow the failure modes of the policies in its tenant-slot call. `useLease` removes lease-served policies from the call before it is sent, and `failClosed(c)` was evaluated afterwards. So when an enforce `fail_closed` batched policy was served from its lease, a quota-only call that failed or answered `quota_unseeded` became `fail_open`, and the request was admitted without its quota. A request that reserved in the same second got a 503. `checkRedis` now records `c.closed` (an enforce `fail_closed` policy is in the call) before leases serve any of the call's policies. The unseeded check and `failed()` use that flag. `TestQuotaFailureModesLease` covers both cases (failed and unseeded) and fails without the change.
6. **A managed gateway without Redis warns of quota overrides it cannot count** (RL-10). A config with plan quotas is refused without Redis (`checkRedis`, ADR-0070). Quota overrides, however, come with the identity, and nothing checked them: the consumer's override quota was silently not enforced (`limits.checkRedis` returns at once when there is no Redis). Refusing the identity, as a config is refused, would also hold back key revocations and suspensions. So the identity is applied, and its quotas stay not enforced, which is what ADR-0070 gives a quota-only call that fails (fail_open). Each identity version that has consumers with a quota override (one with a daily or monthly quota) is logged as a warning: "quota overrides are not enforced: quotas are counted in Redis (RL-10), but SPILLWAY_GATEWAY_REDIS_ADDRS is not set", with `identity_version` and `consumers` (a count, no names). It comes from a new `managed.Options.IdentityApplied` hook. A metric would also need a row in design.md's metrics table, so it is offered to the user as P39 instead of added.

### Tests, docs and the flusher

7. **Flaky tests from main CI run 45487522090 and earlier runs** (carry items 1 and 11). `TestHealthChecks` now meets the node (dial, slot map, version check, script) with a 5 s deadline. The 5 ms budget is kept for the polling, which tolerates individual timeouts. Under CPU load the old first call failed 4 of 30 runs (the review's reproduction); after the change, 30 of 30 passed with `-race` and 12 busy loops. `TestRunFails` now requires an over-admission above the allowed one, not at least 50: the count depends on when the sender's timers fire, and it fell to 30 on a loaded runner while the verdict (FAIL, exit 1) was right. `TestRedisAuth` now waits for the listening port as well as the log line before `MappedPort`. No check that measures Spillway was loosened; these are assertions about the test harness itself.
8. **`Flusher.lastPrune` is under `f.mu`.** In production, every `Flush` runs on the one `Run` goroutine. The integration test, however, runs ten concurrent `Flush` calls on one flusher. The advisory lock orders them in Postgres but gives no happens-before in Go.
9. **Docs.** The README's NFR-05 paragraph said the nightly bench had never been scheduled. In fact, GitHub started the 2026-11-26 03:17 UTC run about 9 hours late (run 45820170869), and that run stored the x64 Intel Xeon Platinum 8573C baseline. So the schedule works, and nothing in `bench.yml` changes (carry item 4). `docs/setup.md`'s benchmark step now describes ADR-0084's shared load-side CPUs and the gate's real baseline rule. The README's Known limits gains OB-06's exemplars in dev, the demo and kind (item 10).

### For the user (not changed here)

10. **OB-06 exemplars and the Collector's tail sampling.** At ratio 1 (dev, demo, kind), every request's exemplar carries its trace ID. The Collector keeps errors, requests over 500 ms and 10% of the rest, so about 9 in 10 exemplars of ordinary requests point at traces Tempo never stored. Options: (a) keep it, as a known limit (now in the README); (b) a 10% trace-ID-ratio head sampler at the gateway, with the Collector keeping every head-sampled trace, which changes OB-02's "sample 100% at the gateway"; (c) attach exemplars only to requests the Collector is sure to keep (errors and slow requests), which changes OB-06's "for sampled traces".
11. **(P37, proposed) RL-10's failure-mode wording.** The applied P24 text says "(fail-closed if any enforce policy there is, otherwise not enforced; fail-open when there is none)". Read literally, an enforce `fail_open` policy would make an unseeded quota a 503. ADR-0070 and the code require an enforce **`fail_closed`** policy. Proposed: "…(fail-closed if any enforce policy there is fail_closed, otherwise not enforced; fail-open when there is none)…".
12. **(P38, proposed) Chaos "Redis +50 ms" recovery rule** (carry item 8). The rule requires every answer from +45 s to +60 s to be decided by Redis, with no Redis error. One host stall longer than the 5 ms budget (ADR-0027) fails it, and ADR-0074's stall-tolerance section does not cover this rule. The single failure (58e8641 run 1) happened in the same verify run as a 2,040 ms burst of Redis errors in NFR-04. The review found no race in the breaker, refill or deny-cache code. The 429s that the rule counts as decided are classified correctly for `test/chaos/latency.yaml` (carry item 7). Proposed, as ADR-0034 does for NFR-04: excuse one burst of Redis-error or undecided answers of at most 1,000 ms after +45 s; require none outside it, and at least one decided answer in the last 5 s. The alternative is a threshold such as ≥ 99.5% decided. Until the user decides, the rule stays as it is.
13. **(P39, proposed, optional) A metric for item 6**, e.g. `gw_quota_overrides_unenforced` (gauge: consumers with a quota override that this gateway cannot count), as a new row in design.md's metrics table.
14. **Kind Redis memory** (ADR-0085 item 10, carry item 3). Each Redis container's limit is 64 Mi, while compose's `redis.conf` sets `maxmemory 256mb` with `noeviction`. A node that grows past about 60 MB is OOM-killed before `noeviction` or `SpillwayRedisMemoryHigh` can act. Options: (a) a kind-only `maxmemory 48mb`, through an extra include, so that `noeviction` and the alert act first; (b) a limit of at least 320 Mi, about 1.5 GB more across the six pods, against the kind memory plan. Either way, a static test that each limit exceeds `maxmemory` would follow.
15. **NFR-05 gate design** (carry items 9 and 10; the gate rule is not changed). The tolerance is the baseline's spread inside one run set on one runner, but comparisons cross runners, and the confirming re-run uses the same runner. Options: (a) run the confirming re-run as a separate job, so it gets a fresh runner; (b) tolerance = max(10%, spread of the metric's medians across the last N eligible baselines on that CPU model); (c) compare with the median of the last N baselines instead of the newest one; (d) judge p99 only when throughput also moves, or widen p99's threshold (a re-baseline); (e) keep the current rule and accept between-runner noise as a known limit (today's decision, ADR-0088). x64 `main` baselines exist only on AMD EPYC 9V74, Intel Xeon Platinum 8573C and 8370C. Models seen without one are AMD EPYC 7763, AMD EPYC 9V45 and Intel Xeon 6975P-C. Options: let the nightly runs accumulate baselines (no change), dispatch a few gated `main` runs to seed them, or accept x64 NFR-05 as model-dependent (ADR-0089, as now).
16. **P35 and P36** (ADR-0084, ADR-0087) are still proposed and unapplied: the NFR-02 row text, and the `cp_quota_*` rows in the metrics table.

## Consequences

- The chart's guidance no longer opens an IP-spoofing path. Deployments that want per-client IP limits behind a NodePort must use `Local` or a real L7 proxy.
- A route to the control plane's REST port through the edge is refused by the NetworkPolicy as well as by RBAC.
- The exporter's password reaches only the Redis nodes; Postgres on kind runs with a default seccomp profile, no privilege escalation and five capabilities, and a static test keeps every kind pod hardened.
- Lease-served requests follow their call's quota failure mode, so during a Redis outage or before a re-seed they are answered 503 under a `fail_closed` policy, as reserving requests already were.
- A Redis-less managed gateway logs a warning for every identity version with quota overrides; the quotas stay not enforced.
- Follow-ups: the user's decisions in items 10–16; a default-deny policy for `spillway-deps`.

## Alternatives considered

- **Refusing an identity with quota overrides on a gateway without Redis** — it would also hold back key revocations and suspensions in the same identity version.
- **A per-request log or metric when a quota is skipped for lack of Redis** — it costs work on every request for a deployment-time mistake that one warning per identity version reports.
- **redis_exporter's `--redis.password-file`** — needs a generated file holding the password (item 3). The egress rule covers the leak.
- **Excluding every pod but a named list from the control plane's REST** — it would break the seed Job or any operator Job not on the list, for no gain over excluding the only internet-facing pods.
