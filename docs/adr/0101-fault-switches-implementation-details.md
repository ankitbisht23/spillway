# 0101. Fault switches: implementation details

- **Status:** Accepted
- **Date:** 2026-11-27
- **Requirement IDs:** SC-03, SC-08, RL-22 – RL-24, GW-13, GW-14, CP-12, CP-13

## Context

ADR-0095 §5 settles the fault switches: two faults (`redis-cut` for D5, `upstream-slow` for D6), one operation `PUT /api/v1/demo/faults/{name}` (`setDemoFault`, admin only, audited, 404 when demo mode is off), the toxics, the control plane talking to toxiproxy at `SPILLWAY_CP_DEMO_TOXIPROXY_URL`, and `make demo-fault-redis`, `make demo-fault-upstream` and `make demo-fault-clear` running `demo-traffic fault`. ADR-0100 left `faults` in `getDemo` and the toxiproxy setting to this task. Building them (task fault-switches, ADR-0093) left some details open; accepted ADRs are not edited, so the choices are recorded here.

## Decision

1. **What "active" means.** A fault is active while **any** of its toxics is on any of its proxies. A change that failed half-way (ADR-0095 §5 leaves what it changed in place) therefore shows as on until it is switched off, so "off" in `getDemo` always means no toxic is left. `DemoFault.active` is nullable: **null** when toxiproxy could not be read or lacks one of the fault's proxies (for example before `make demo` created them). `setDemoFault` never answers null. `getDemo` reads all states with one `GET /proxies` (each proxy lists its toxics), cached for 1 s per control-plane process (ADR-0095 §2); a switch empties the cache, so the next `getDemo` reads toxiproxy again.
2. **A switch converges.** On, it adds each of the fault's toxics a proxy lacks; off, it deletes each that is there; a fault already in the state asked for gets no toxiproxy write. It checks first that every proxy of the fault exists (else 503, nothing changed), then reads the state back and answers 503 if toxiproxy did not keep it. One switch runs at a time per process (a mutex); the demo runs one control-plane replica. Each toxiproxy call has the 2 s timeout of ADR-0095 §5.
3. **Answers.** Order of checks after the guard and RBAC: an unknown fault name → 404 `not_found` (`no such fault: want redis-cut or upstream-slow`; the generated router does not check the path enum); a body without `active`, or with `active: null` → 400 `invalid_request` (`body: active: required`; a Go bool alone cannot tell missing from false); a note of 0 or over 500 characters → 422 `validation_failed` on `note`; no toxiproxy configured → 503 `unavailable`; a toxiproxy failure or a missing proxy → 503 `unavailable` whose message names the proxy and the toxic only (`toxiproxy has no proxy demo-upstream-2 (make demo creates it)`, `toxiproxy could not change demo-cut-up on demo-redis-3`, `toxiproxy could not be read`). Toxiproxy's own error goes only to the control plane's log (`cause`), with the fault, the state asked for and the request ID.
4. **The audit record.** Action **`demo_fault.update`** and entity `demo_fault` (ADR-0095 §5 wrote action `update`; the log's actions are `<entity>.<verb>`, ADR-0040, as ADR-0100 §5 did for the janitor), entity ID the fault's name (the store's audit writer gains a text entity ID for it), diff `{"before": {"active": …}, "after": {"active": …}}`, the note, the request ID, no config or identity version. It is written once toxiproxy has confirmed the change; a switch to the state the fault already had is still one record (ADR-0095 §5's "every successful PUT"); a failed switch writes none.
5. **`SPILLWAY_CP_DEMO_TOXIPROXY_URL`** is read only in demo mode, where it is required; it must be an `http` or `https` URL with a host and no user info, query or fragment (the check the Prometheus URL already has). With demo mode off it is ignored, whatever its value. Only `deploy/compose/demo.compose.yml` sets it (`http://toxiproxy:8474`); compose, Helm and kind never do.
6. **One toxiproxy client.** The demo-seed task's `internal/demo.Toxiproxy` gains `ProxyToxics`, `AddToxic` (an existing toxic of that name is not an error) and `DeleteToxic` (a missing one is not an error); the control plane's fault code (`internal/controlplane/demo.Faults`) uses it, so `demo-traffic proxies` and the switches share one client.
7. **The make targets** run `deploy/demo/demo.sh fault`, which runs `demo-traffic fault` in a one-off container of the **`demo-seed`** service with `--no-deps`: that service already carries the control plane's and Keycloak's in-network URLs and the `spillway-ci` client, and the `demo-traffic` service of ADR-0096 does not exist yet (traffic-sim may move the targets to it). `ON` must be `1` or `0`; anything else prints the usage and exits 2.
8. **`demo-traffic fault [-note text] <redis-cut|upstream-slow> <on|off>` and `demo-traffic fault [-note text] clear`** ask `GET /api/v1/demo` first, so with demo mode off they print exactly `demo-traffic fault: demo mode is off (GET /api/v1/demo answered 404)` and exit 1 before any switch (ADR-0095 §1, ADR-0098 g6). Then one `setDemoFault` per fault, printing `redis-cut: on` and so on. The default note is `demo-traffic fault <arguments>`. The token and the client secret are never printed.
9. **Reset and down.** `make demo-reset` switches both faults off first (ADR-0094 §1); if the control plane cannot, it creates the demo proxies again with `demo-init` (no toxics), since a reset keeps the proxies and restarts the demo gateways anyway. `make demo-down` switches both faults off through the API when the demo control plane is running (a warning otherwise), then deletes the proxies as before, which removes any toxic left.
10. **No Docker socket, checked.** `test/deploy` (a static Go test, run by `make test`) fails if any service of the three compose files mounts a container-runtime socket or the directory that holds it (short and long volume forms), or if any compose file, Helm chart file, kind file, Dockerfile, demo script, chaos file or workflow names `docker.sock`, `containerd.sock` or `podman.sock`. `test/load/scaling.sh` reads container CPU time from the host's socket on the host, not from a container, and is outside the scanned roots. The key directories are never read.
11. **Tests and their rules.** Go unit tests with a fake toxiproxy (on, off, idempotence, missing proxy, failure half-way and completion, read-back, cache), the API's checks and RBAC, `demo-traffic fault` against a fake control plane (no token or secret printed); an integration test against compose's toxiproxy with test-made demo proxies, deleted afterwards (toxics, `getDemo` states, roles, audit records, a missing proxy); and two demo-stack tests in `test/demo` (`make test-demo`), from the host against gateway-1, the only replica with host ports:
    - **TestFaultRedisCut (D5).** pro-co-mobile: before, Redis decides ≥ 90% of catalog and payments and every answer is 2xx; `make demo-fault-redis ON=1`; for 10 s, catalog 50 rps ≥ 99.9% 2xx (fail-open), payments 10 rps all 503 (fail-closed), orders 66 rps admits (2xx − 66) ÷ 10 s within ± 10% of 33/s with every other answer 429 (degraded at limit ÷ 3 live replicas, RL-23, RL-24), no answer decided by Redis, every Redis error `timeout` or `conn` and `gw_redis_errors_total{kind="script"}` unchanged, each route's median latency ≤ the median before + 10 ms, ≥ 99% of gateway-1's Redis checks in `le="0.01"`; `make demo-fault-redis ON=0`; Redis decides again within 5 s and ≥ 90% of the next 5 s.
    - **TestFaultUpstreamSlow (D6).** orders 30 rps: before, 10 s of steady load, all 2xx and the circuit closed; `make demo-fault-upstream ON=1` for 20 s; the circuit opens within 15 s and `circuit_open` answers grow; retries within budget by §13's rule (for scrapes i < j read at most 9.9 s apart, ΔR(i, j) ≤ 0.2 × ΔQ(k, j) + 30; ≥ 30 windows of 8–9.9 s, every 1 s scrape answered, ≤ 2 s apart) and at least one retry sent; after `ON=0` the circuit closes within 30 s and ≥ 99% of answers due 20–30 s after are 2xx.

    Host and Docker Desktop stalls (ADR-0026, ADR-0027, ADR-0034) cannot fail these by themselves: answers are placed by due time; every GCRA burst holds 2 s of its rate, so requests a stall holds back are still admitted, and D5's count allows ± 1 s of the rate; latency compares medians; 1% of Redis checks may exceed 10 ms (a stall lengthens only the checks in flight); D6's budget rule follows from the gateway's grant rule whatever the timing, and a stall only widens a scrape's send-to-receive span, which bounds its read time (fewer pairs qualify; 1 s scrapes left 42 windows in each run against the 30 required); each wait (5 s, 15 s, 30 s) is many times the longest stall. Every test switches both faults off when it ends, also on failure (`make demo-fault-clear` in a cleanup), then removes and reports any demo toxic still left. These are this task's checks; ADR-0098's D5 and D6 (three replicas, 20 s and 30 s windows) stay verify-m8's.

    **Measured exception (not changed here; the user's call).** One line is not stall-immune: TestFaultRedisCut's "every answer before the cut is 2xx" for `payments`, whose policy is `fail_closed`. A Redis call that a stall pushes past its 5 ms budget takes its failure mode (ADR-0098's stall table), and for `fail_closed` that is a 503. It failed 1 run out of 10 (four earlier runs, then six on 2026-11-27 incl. three full `make test-demo` suites): 4 of 50 `payments` answers were 503 while `catalog` (`fail_open`) and `orders` (`degraded`) stayed 2xx, and gateway-1's `gw_redis_errors_total{kind="timeout"}` grew by 25 in that phase (Prometheus); the run followed TestDemoReset's gateway restart, but two runs started right after `make demo-reset` passed, so the restart alone does not explain it. The test now logs each non-2xx answer before the cut with its `Spillway-Redis-Error`. A stall-immune form would be ADR-0098 d5.0's (≥ 90% decided by Redis) plus "every `payments` answer before the cut is 2xx or a `fail_closed` 503 whose `Spillway-Redis-Error` is `timeout`"; it is proposed in the PR, not applied.
12. **Checklist.** The M8 box "Traffic simulator and toxiproxy-only fault switches for D1–D7 (SC-02, SC-03)" stays unticked: SC-02 is not on `main`, and ADR-0093 assigns the box to playground (its buttons complete SC-03). P42 and P45's `setDemoFault` row are applied to docs/design.md.
13. **D6's retry-budget rule (amends ADR-0098 d6.3).** The user's decision of 2026-11-27 (option A below, the user's words: "A do it").

    ADR-0098 d6.3 as accepted: "every rolling window (scrape pairs i < j with recv_j − send_i ≤ 10 s and send_j − recv_i ≥ 8 s, the earliest i for each j) has ΔR ≤ 0.2 × ΔQ + 30, R = `gw_retries_total{upstream="orders", outcome="sent"}`, Q = `gw_upstream_duration_seconds_count{upstream="orders", attempt="1"}`; coverage: every scrape answered, consecutive scrapes at most 2 s apart, at least 30 windows per replica."

    d6.3 from now on: "Retries within budget (GW-13, per replica): for every pair of answered scrapes i < j with recv_j − send_i ≤ 9.9 s, ΔR(i, j) ≤ 0.2 × ΔQ(k, j) + 30, where k is the latest answered scrape with send_i − recv_k ≥ 10 s (pairs whose i has no such k are not checked), R = `gw_retries_total{upstream="orders", outcome="sent"}`, Q = `gw_upstream_duration_seconds_count{upstream="orders", attempt="1"}`; coverage: every scrape answered, consecutive scrapes at most 2 s apart, and at least 30 scrapes j per replica that have a checked pair with send_j − recv_i ≥ 8 s (a window); the load runs steadily for 10 s before the fault so that the first windows of the fault have their k. The tightest pair and the totals of `sent` and `budget_exhausted` are printed."

    **Why it follows from GW-13.** The budget (`internal/resilience/budget.go`, ADR-0030) grants a retry at s only while R(s − 10 s, s] + 1 ≤ 0.2 × Q(s − 10 s, s] + 30, where Q counts first attempts that ended in its window, and its window of 100 buckets of 100 ms covers at least 9.9 s and at most 10 s. Let s be the last retry counted in ΔR(i, j). Every retry in ΔR(i, j) was granted in (t_i, s], and s − t_i ≤ t_j − t_i ≤ recv_j − send_i ≤ 9.9 s, so (t_i, s] lies inside s's window: ΔR(i, j) ≤ R(s − 10 s, s] (counting s itself) ≤ 0.2 × Q(s − 10 s, s] + 30. Since t_k ≤ recv_k ≤ send_i − 10 s < s − 10 s and s ≤ t_j, Q(s − 10 s, s] ≤ ΔQ(k, j). (`attempt="1"` is observed just before the budget counts the same attempt (`internal/proxy/retry.go`), so the metric never lags the budget.) A correct gateway therefore passes whatever the load's shape; the old form compared ΔR with ΔQ over the same window, which follows from GW-13 only while first attempts end at a steady rate.

    **Why it was needed.** TestFaultUpstreamSlow failed 3 runs out of 3 under the old form (2026-11-27), each time on the budget check alone: 48–49 windows, 7 over, tightest at 113–114% of the allowance (retries sent 70–71, `budget_exhausted` 14–16), every other D6 check passing (circuit open 6.3–6.4 s after the fault, closed 7.3–7.6 s after its end). In D6 first attempts fall from about 30/s to almost none once the breaker opens, so retries granted in the fault's first seconds are paid for by healthy first attempts that ended just before the old window began.

    Options put to the user: **A** (taken) the rule above; **B** keep the old form and judge only windows that start after the breaker opened (narrows D6); **C** rebuild the budget's view per request from the client's answers (exact in principle, but it depends on host clock timing exactly where the budget is binding, so host stalls could fail it).

    It applies to this task's TestFaultUpstreamSlow and to verify-m8's d6.3 (task verify). Every other D6 check (d6.1, d6.2, d6.4) and ADR-0031's rule (b) for verify-m4 stay as they are. ADR-0098's status line points here.

## Consequences

- Buttons (playground) and make targets share one path: the same RBAC, audit record and 404, and toxiproxy's state is the only state, so a control-plane restart loses nothing.
- A viewer sees fault states in `getDemo` (null while toxiproxy cannot say) but cannot switch them.
- `make test-demo` grows by about two minutes (D5 about 30 s, D6 about 65 s).
- playground adds the buttons on `getDemo`'s states and `useCan("setDemoFault")`; traffic-sim's `run --scenario=d5|d6` can switch faults through the same operation.

## Alternatives considered

- **"Active" only when every toxic is in place** — a half-failed switch-off would show off while toxics remain.
- **`getDemo` answering 503 when toxiproxy cannot be read** — the UI hides the Playground on any `getDemo` error (ADR-0095 §2), so a toxiproxy hiccup would hide it.
- **Adding toxics blindly and treating 409 as done** — kept as a fallback in `AddToxic`, but reading first lets a same-state switch write nothing, as ADR-0095 §5 asks.
- **A separate `demo-fault` compose service for the make targets** — another service to name, label and keep out of `make demo`'s list, for what `demo-seed`'s settings already cover.
- **A shell or `make`-level check for the socket** — the Go test parses compose's volume forms and runs in `make test` without new tools.
