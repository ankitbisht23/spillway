# 0103. Playground: implementation details

- **Status:** Accepted
- **Date:** 2026-11-28
- **Requirement IDs:** SC-04, UI-07, SC-03, SC-08, CP-12, CP-13, UI-04, UI-06

## Context

ADR-0096 §3 settles the Playground: `startPlaygroundRun`, `stopPlaygroundRun` and `openPlaygroundStream` under ADR-0095's demo guard, the generator in the control plane with per-tenant Playground keys (ADR-0095 §3), the caps, the per-run SSE stream and the screen with the admin fault switches. ADR-0100 and ADR-0101 left `SPILLWAY_CP_DEMO_GATEWAYS`, `getDemo`'s `playground` part, the generator's use of `demo.Keys.Expiry` and the buttons to this task. Building them (task playground, ADR-0093) left details open; accepted ADRs are not edited, so the choices are recorded here.

## Decision

1. **The start's body is one object, `PlaygroundRunRequest`,** with `kind` (`custom` or `scenario`) and optional `tenant`, `route`, `rate`, `duration_s` and `scenario`, rather than a `oneOf`, which oapi-codegen turns into a union the handler would have to unpick. The handler checks it before anything else: an unknown field, a wrong JSON type or an unknown `kind` → 400 `invalid_request`; a missing field, a value outside its range (rate 1–200, `duration_s` 5–60, the three tenants, routes and scenarios) or a field the kind does not take (`scenario` on a custom run; `tenant`, `route`, `rate` or `duration_s` on a scenario run) → 422 `validation_failed` naming that field. The run ID in the path is a plain string of at most 64 characters, so any ID that is not the caller's run, malformed or not, is the same 404 `not_found` (`no such run`).
2. **A start reserves before it prepares.** Admission checks every cap under one lock and reserves the run (it counts as active at once, with an estimated end 15 s past its duration for `Retry-After`) and its start in both rolling hours. Then the Playground makes sure each tenant of the run has a key with at least 5 minutes left, issuing one through `demo.Keys.Expiry` (the 30-minute rule) when not, and sends one probe request per tenant key to every gateway (`X-Request-Id: pg-probe-<uuid>`, not counted in the run). A freshly issued key is probed again every 100 ms, for at most 10 s, until no gateway answers 401 (as `demo-traffic`, ADR-0102 §4), so no counted request is a 401 of a key that has not reached the gateways yet. If no probe got an answer the start is 503 `unavailable` (`no demo gateway answers`); a missing `<tenant>-playground` consumer (or tenant) is 503 too. A refused start gives back its reservation and its start. A start on a fresh key can therefore take a few seconds (one identity version to the gateways); the screen shows "Starting the run" meanwhile.
3. **Times.** `started_at` is when the schedule starts, after the probe; `ends_at` is `started_at` plus the duration. Request i of a load is due at `started_at` + i ÷ rate whatever happened before it (open model); a request due while 256 of the run's requests are in flight is dropped and counted. The schedule stops at `ends_at`; then the run waits for its requests in flight (each has a 5 s timeout), writes a last tick for that remainder and the `end` event. Round robin is one counter over the whole run (request n of the run goes to gateway n mod 3, whatever its tenant).
4. **Counting.** By status: `ok` 2xx, `limited` 429, `forbidden` 401 and 403, `failed` 503, `other` any other status **or no answer within 5 s**. Latency runs from each request's due time to the end of its body, in HDR histograms (µs, 3 significant digits, top 10 s) per tick and per run; `p50_ms` and `p99_ms` are null without answers. A tick is written every second of the control plane's clock while the run sends; its `replicas` lists every gateway (0 when none got a request that second), named by the gateway URL's host name (`gateway-1`), or host and port when two share a host name; its `last` is each tenant's latest answer so far, kept across ticks.
5. **The stream** sends `ready`, then the ticks written after it opened (no replay), then `end`; a stream opened after the end gets `ready` (with `state: ended`) and `end`. A token that expires ends the stream with `end`/`token_expired` and the totals so far while the run goes on. A stopped run's `end` has reason `stopped`; at shutdown (`http.Server.RegisterOnShutdown`) every run ends with reason `shutdown`, its requests in flight are cancelled, and starts are refused with 429. A run's results go 5 minutes after its end.
6. **`Retry-After`.** Past an active-run cap: whole seconds until the earliest `ends_at` among the runs that fill it (at least 1). Past an hourly cap: until the start that makes the hour full is an hour old. Past a stream cap, or while shutting down: 5 s.
7. **The client IP, for now, is the TCP peer's address** (IPv6 per /64), in a request-context value set in front of the demo guard; it is never logged, stored or audited. ADR-0097 §2's `SPILLWAY_CP_TRUSTED_PROXIES` and `CF-Connecting-IP` arrive with demo-share, which replaces only that function. Locally every browser reaches the control plane from Docker Desktop's one address, so the per-IP cap of one active run applies to all local users together.
8. **Audit records** follow the log's `<entity>.<verb>` convention (ADR-0040; as ADR-0100 §5 and ADR-0101 §4 did): `playground_run.create` and `playground_run.delete` (ADR-0096 §3 wrote `create` and `delete`), entity `playground_run`, entity ID the run's UUID, diff `{"after": {kind, tenant, route, rate, duration_s, scenario}}` or `{"before": …}` (absent fields null), the caller as actor, the request ID, no version. The start's record is written once the run started; if it fails, the run is stopped and the start answers the error. A stop of one's own run that already ended (within its 5 minutes) is still 204 and one record, as a same-state fault switch is (ADR-0101 §4). Keys are issued through the store as actor `system:playground` (name `Playground`, no roles) with request ID `playground-key-<uuid>`: the usual `key.issue` record and identity version, with the key's ID and prefix only.
9. **Keys** live in the active control plane's memory only; a restart loses them and the next run issues new ones. They are never revoked: they expire within 30 minutes and the janitor deletes them an hour after (ADR-0095 §4). Log lines name a key by its ID (`playground key issued`, with tenant, `key_id` and `expires_at`); the start and end lines carry the run ID, the caller's `sub`, the shape and the totals.
10. **`SPILLWAY_CP_DEMO_GATEWAYS`** is read only in demo mode, where it is required: one or more distinct `http` or `https` base URLs, comma separated, each with a host and no user info, path, query or fragment. Only `deploy/compose/demo.compose.yml` sets it (`http://gateway-1:8000,http://gateway-2:8000,http://gateway-3:8000`). `getDemo`'s `playground` (`max_rate` 200, `max_duration_s` 60, the caller's `active_runs`, and `runs_left_this_hour`, the smaller of the caller's and its IP's) is a new required response property, which oasdiff accepts; `client_ip` stays demo-share's (ADR-0100 §2).
11. **The screen.** The app shell's demo probe stays once per session (ADR-0100 §8); the screen reads `getDemo` again under its own query key every 5 s while it is open (fault states, runs left), so a failed refetch never hides the navigation entry. Limits come from `getDemo`: the chart's limit line is the rate per second of the tenant's plan for `orders` and of the route's policy for `catalog` and `payments`; the token bucket is `r` of that policy's item in the latest `RateLimit` (`consumer-plan`, `catalog-limit`, `payments-limit`) against that limit's burst, as a `<meter>`. The run's stream uses fetch through the session (token in `Authorization`, same origin); a dropped connection reconnects up to three times (1, 2, 4 s), `token_expired` at once, a 4xx stops it with the error. Non-admins see no fault section at all (ADR-0095 §2); admins get each switch behind a confirmation with an optional note (1–500 characters).
12. **The Playwright flows run on the demo stack, in a target of their own,** `make test-e2e-demo` (`make demo`, `web/e2e/playground.spec.ts` with `web/playwright.demo.config.ts`, then `make demo-down` whatever the result), not in `make test-e2e` as ADR-0098's context put it: `make test-e2e` and CI's e2e job run on the dev stack with demo mode off, where `e2e/demo.spec.ts` checks the hidden Playground and the probe's 404, and the Playground needs demo mode, the seed and three managed gateways. `make test-e2e` ignores the Playground spec. CI does not run it (as verify-m6's exit flow). Its same-origin check allows exactly one other URL, Keycloak's token endpoint, should a token refresh fall due during a flow; every other request after the login must go to the control plane's origin. On the app's pages the flows allow no console message of any type.

## Consequences

- The Playground works from `make demo` for every role; admins also switch D5's and D6's faults from it, which completes SC-03 and, with traffic-sim, the SC-02/SC-03 box. This is the last task that adds a guarded surface, so it ticks the SC-08 box (ADR-0093 D27); grafana-demo ticks the Playground/Grafana box.
- A start that needs a new key waits for the gateways to have it, at most 10 s, instead of counting 401s.
- The Playground's browser flows need `make test-e2e-demo` (about 4 minutes on a built stack, plus `make demo` and `make demo-down`), outside CI.
- demo-share changes only the client-IP function to apply `SPILLWAY_CP_TRUSTED_PROXIES`.

## Alternatives considered

- **A `oneOf` request body** — a generated union type for two shapes the handler validates anyway.
- **`format: uuid` on the run ID** — a malformed ID would be 400 instead of the 404 every other unknown run gets.
- **Counting the first seconds of a new key's 401s** — the screen would show `forbidden` answers that say nothing about limits.
- **Replaying past ticks to a stream opened mid-run** — ADR-0096 says ticks while running; the screen opens the stream right after the start, so it misses nothing it needs.
- **Running the Playground flows inside `make test-e2e`** — it would have to boot the demo stack instead of the dev stack, which changes every other flow's stack and CI's e2e job.
